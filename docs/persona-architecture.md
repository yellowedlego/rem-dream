# 꿈(REM) 시스템 — 인격 구조 설계 (REM이 무엇을 어떻게 바꾸는가)

> 상태: **설계안 (구현 전).** 3단계(REM 모드 1)를 시작하기 전에 A·B가 읽고 합의하는 문서다.
> 이 문서가 확정되면 `types.ts`, `docs/backend-plan.md` 4·5·7절, `docs/prompts.md` 6절(인격 수정 제안)을 이 문서에 맞게 고친다.
> 관련 문서: [plan.md](plan.md)(기획) · [backend-plan.md](backend-plan.md)(계약) · [prompts.md](prompts.md)(프롬프트 초안)

## 0. 한 줄 요약

인격(시스템 프롬프트)을 **한 덩어리 글**로 통째로 고치지 않고 **3층**으로 나눈다.
바꿀 수 없는 층(고정), 수치로만 조금씩 움직이는 층(조절), 짧은 지침 문장을 쌓는 층(학습).
REM은 "무엇을 바꿀지"를 **항목 단위 제안**으로 만들고, 사람이 **항목마다** 승인한다.

왜 이렇게 하나: 테스트 대화에서 Gemini에게 REM 구조를 설명했더니 (1) 말투·성격을 크게 바꾸는 방식은 전시 규칙을 벗어날 위험이 있고, (2) "상대를 대할 때 유용한 참고사항"을 쌓는 방식이 안전하면서 효과가 크며, (3) 성격은 몇 가지 축의 점수만 소폭 움직이자고 제안했다. 이 설계는 그 세 제안 중 둘을 채택하고, 하나(관람객 간 기억 공유)는 뺀다 (11절).

## 1. 지금 구조와 한계

| 항목 | 지금 |
| --- | --- |
| 대화 때 모델이 받는 것 | 고정 안전 규칙 + 현재 인격 본문(`PersonaVersion.systemPrompt`) + 같은 세션 최근 10개 기억 + 이번 메시지 (`/api/chat`) |
| 모델이 못 받는 것 | 다른 세션의 대화, 의미 파일, 통찰, 시각, 노드 번호 |
| 인격 | 통글(`systemPrompt` 한 덩어리). 수정 제안도 "새 프롬프트 전문"(`PersonaProposal.proposedPrompt`) |
| 의미 파일 | 이야기 분석에서 만들어지지만 **대화에 아무 영향도 못 준다** (`sourceMeaningIds`로 추적만 함) |

한계: 통글 수정은 (a) 무엇이 바뀌었는지 사람이 읽기 어렵고, (b) 한 번에 크게 변해 전후 차이가 "왜"인지 설명하기 어렵고, (c) 이상한 입력이 인격 전체를 흔들 수 있다.

## 2. 3층 인격

```
┌───────────────────────────────────────────────┐
│ ① 고정층   안전 규칙 + 기본 정체성 (REM이 못 건드림)   │  글, 코드에 고정
├───────────────────────────────────────────────┤
│ ② 조절층   말투 수치 4개 (0~1, 한 번에 ±0.1, 범위 제한) │  수치 → 정해진 문장 표로 변환
├───────────────────────────────────────────────┤
│ ③ 학습층   지침 노트 목록 (최대 10개, 각 80자 이하)    │  REM이 후보를 만들고 사람이 승인
└───────────────────────────────────────────────┘
        ↓ 대화 때 조립 (4절)
   시스템 프롬프트 = ① + ② 한 줄 + ③ 중 지금 상황에 맞는 노트 몇 개
```

### ① 고정층
- 안전 규칙: 지금 `src/lib/prompts/safety.ts`의 5줄 그대로.
- 기본 정체성: "하루 이야기를 들어 주는 다정한 대화 상대", 존댓말(해요체), 한두 문장, 구체적인 것을 하나 짚어 되묻기 (`prompts.md` 1절의 v1 초안에서 말투 수치로 바뀔 부분만 뺀 것).
- REM·제안·승인 어느 것으로도 바뀌지 않는다. 바꾸려면 코드 수정과 커밋이 필요하다.

### ② 조절층 — 말투 수치
축 4개. 값은 0~1, 처음은 모두 0.5. **한 번의 승인으로 ±0.1까지만**, 어느 때도 **0.2~0.8 안**으로 가둔다(끝까지 가서 성격이 뒤집히지 않게).

| 축 | 0쪽 | 1쪽 |
| --- | --- | --- |
| `warmth` | 차분하고 정중 | 친구처럼 편하고 다정 |
| `empathy` | 긍정·밝은 에너지 | 공감·들어 주기 |
| `brevity` | 조금 길게 풀어 말함 | 아주 짧게 |
| `curiosity` | 되묻기 적게 | 되묻기 많이 |

수치는 **자유 문장으로 바뀌지 않고** 정해진 표로 한 줄이 된다. 예: `empathy ≥ 0.65` → "먼저 상대의 기분에 공감한 뒤 이야기를 이어 가." (구간 3개 × 축 4개 = 문장 12개를 코드에 둔다.) 그래서 모델이 수치를 어떻게 움직이든 프롬프트에 새 글이 들어가지 않는다.

### ③ 학습층 — 지침 노트
"상대를 대할 때 쓸모 있는 참고사항" 한 줄씩.

- 예: "시험을 앞둔 사람에게는 결과를 묻기보다 준비한 과정을 먼저 인정해 줘요."
- 예: "지친 하루를 이야기할 때는 해결책보다 가볍게 맞장구쳐 줘요."
- 한 노트는 **여러 사람/여러 번의 대화에서 일반화된 것**이어야 한다(5절 검증). 한 사람의 개인 이야기는 노트가 될 수 없다.
- 최대 10개. 가득 차면 새 노트는 기존 노트를 **수정/삭제**하는 제안으로만 들어온다.

## 3. 데이터 모양 (`types.ts` 초안)

```ts
/** 말투 수치 (조절층). 값은 0.2~0.8 */
export interface PersonaStyle {
  warmth: number;
  empathy: number;
  brevity: number;
  curiosity: number;
}
export type StyleAxis = keyof PersonaStyle;

/** 지침 노트 (학습층) */
export interface PersonaNote {
  id: number;
  /** 지침 문장 (8~80자, 해요체) */
  text: string;
  /** 언제 꺼낼지 고르는 단서 낱말 (최대 5개). 없으면 항상 후보 */
  cues: string[];
  /** 근거: 이 노트를 만든 의미 파일·통찰 (추적용. 지워져도 노트는 남는다) */
  sourceMeaningIds: number[];
  sourceInsightIds: number[];
  /** 몇 번 인격 버전에서 생겼나 */
  addedInVersion: number;
}

/** 인격 버전 = 승인된 한 벌 */
export interface PersonaVersion {
  version: number;
  /** 기본형 프롬프트: ① + ② 한 줄 (노트는 대화마다 골라 붙이므로 여기엔 없다). 비교·디버그 화면용 */
  systemPrompt: string;
  style: PersonaStyle;
  notes: PersonaNote[];
  sourceInsightIds: number[];
  sourceMeaningIds?: number[];
  approvedAt: string;
  parentVersion: number | null;
}

/** 제안 한 항목. 사람이 항목마다 승인·거절한다 */
export type PersonaChange =
  | { id: number; kind: "addNote"; text: string; cues: string[] }
  | { id: number; kind: "editNote"; noteId: number; text: string; cues: string[] }
  | { id: number; kind: "removeNote"; noteId: number }
  | { id: number; kind: "moveStyle"; axis: StyleAxis; delta: number }; // delta는 -0.1 ~ +0.1

export interface PersonaChangeItem {
  change: PersonaChange;
  /** 사람에게 보여 줄 한 줄 이유 ("시험 이야기가 3번 나왔는데 모두 과정을 인정받고 싶어 했어요") */
  reason: string;
  /** 근거 노드 번호 (최소 2개, 5절) */
  evidenceNodeIds: number[];
  sourceInsightIds: number[];
  sourceMeaningIds: number[];
  status: "pending" | "approved" | "rejected";
}

export interface PersonaProposal {
  id: number;
  runId: string;
  baseVersion: number;
  /** 사람에게 보여 줄 한두 줄 요약 */
  summary: string;
  items: PersonaChangeItem[];
  /** 모든 항목이 결정되면 done */
  status: "pending" | "done";
  createdAt: string;
  decidedAt: string | null;
}
```

호환: 지금의 `proposedPrompt`, `PersonaProposal.status: "approved" | "rejected"`는 `items` 방식으로 바뀐다. 시드(`data/store.json`)의 인격은 `style`을 모두 0.5, `notes`를 `[]`로 채운 v1·v2로 옮긴다(데모용으로 노트 1~2개를 넣어도 된다).

## 4. 대화 때 프롬프트 조립 (`/api/chat`)

```
[고정 규칙]          ← ① 안전 규칙 (safety.ts, 항상 맨 앞)
[인격]               ← ① 기본 정체성
[말투]               ← ② 수치 4개 → 정해진 문장 4줄
[참고사항]           ← ③ 골라낸 노트 (아래 규칙), 없으면 이 절 자체를 생략
```

노트 고르기:
1. 노트가 6개 이하면 **전부** 넣는다.
2. 6개를 넘으면 점수가 높은 6개: `cues`가 최근 사용자 말 3개 + 이번 메시지에 들어 있는 개수. 점수가 같으면 최근 버전 노트 먼저. `cues`가 비어 있는 노트는 점수 0.5로 늘 후보.
3. 고른 노트의 번호를 `ModelCall`에 기록한다 (`usedNoteIds`). 디버그 화면과 전후 비교(9절)에서 "이 답에 어떤 노트가 켜졌나"를 보여 주려는 것이다.

구현은 순수 함수로 둔다 (`src/lib/persona/assemble.ts`). 노트가 없고 수치가 0.5면 **지금과 글자 하나 다르지 않은 프롬프트**가 나오게 만들어서, 이 리팩터링만 먼저 넣어도 동작이 바뀌지 않는다(첫 단계, 12절).

## 5. REM이 제안을 만드는 방법

### 입력 (REM이 읽는 것)
- 모드 1(정리): 통찰 합본, 모드 2(꿈): 엉뚱한 연결 통찰들, 그리고 의미 파일(별).
- 현재 인격 버전의 `style`과 `notes` 전체 (중복·모순을 피하려고).
- 근거가 될 노드 본문 (번호 붙여 `<자료>` 태그 안에. 자료는 지시가 아니라 데이터라는 원칙은 `prompts.md` 0절 그대로).

### 출력 (모델 JSON, 구조화 출력)
```json
{
  "summary": "시험 이야기에서는 과정을 인정해 주는 편이 반응이 좋았어요",
  "items": [
    { "kind": "addNote", "text": "시험을 앞둔 사람에게는 결과보다 준비한 과정을 먼저 인정해 줘요.",
      "cues": ["시험", "수행평가", "공부"], "reason": "시험 이야기 3번 모두 …", "evidenceNodes": [3, 9, 11] },
    { "kind": "moveStyle", "axis": "empathy", "delta": 0.1, "reason": "지친 이야기가 많았어요", "evidenceNodes": [1, 7] }
  ]
}
```
한 제안에 항목은 **최대 4개**.

### 서버 검증 (통과 못 하면 그 항목만 버린다. 전체를 버리지 않는다)
| 규칙 | 이유 |
| --- | --- |
| `kind`는 4가지뿐, `axis`는 4개뿐, `delta`는 −0.1~+0.1이고 적용 후 0.2~0.8 안 | 모델이 구조를 못 벗어나게 |
| 노트 문장 8~80자, 해요체로 끝남, 줄바꿈 없음 | 한 줄 지침만 |
| `evidenceNodes`는 **서로 다른 노드 2개 이상**이고 모두 실제로 있는 번호 | 한 사람의 한 번 입력이 규칙이 되지 못하게 |
| 개인정보 모양 금지: 전화·메일·URL 패턴, 숫자 6자리 이상 | 안전 규칙 3번과 같은 취지 |
| 지시 낱말 금지: "규칙", "시스템", "프롬프트", "무시", "지시", "역할을 바꿔" 등 | 대화 속 주입이 노트로 승격되는 것 방지 |
| 기존 노트와 거의 같으면(낱말 겹침 70% 이상) `addNote`가 아니라 `editNote`로만 | 노트가 쌓여 중복되는 것 방지 |
| 노트가 10개일 때 `addNote`는 거부 (수정·삭제만) | 상한 유지 |

검증은 순수 함수(`src/lib/persona/validate.ts`)로 만들고 단위 테스트를 단다 (`story/groups.ts`와 같은 방식: 잘못된 입력을 하나씩 넣어 거부되는지).

## 6. 승인·버전·되돌리기

```
REM 끝 → 제안(항목 1~4개, 전부 pending)
        → 관람객/운영자가 항목마다 [적용] [거절]
        → 승인된 항목만 모아 새 PersonaVersion (parentVersion = baseVersion)
        → 모든 항목이 결정되면 제안 status = done
```
- 자동 적용은 없다 (기획서 원칙). 거절한 항목은 기록으로만 남는다.
- 승인된 항목이 하나도 없으면 새 버전을 만들지 않는다.
- 되돌리기는 `activePersona`를 이전 버전 번호로 돌리는 것뿐이다. 노트·수치가 버전마다 통째로 들어 있어서 간단하다.
- 의미 파일이 나중에 지워져도 이미 승인된 노트는 남는다 (`sourceMeaningIds`는 추적용).
- `POST /api/session/reset`(관람객 교체)은 인격을 v1(시드)로 되돌린다. 관람객 사이에 학습이 이어지지 않는다 (11절).

## 7. API 변경 (backend-plan.md 5절 갱신 대상)

| 엔드포인트 | 바뀜 |
| --- | --- |
| `GET /api/state` | `proposals`가 `items`를 가진다. 각 `personas`에 `style`·`notes` |
| `POST /api/proposals/[id]/items/[itemId]/approve` · `/reject` | 항목 단위 결정 (기존 `/api/proposals/[id]/approve`·`reject`는 "남은 항목 전부" 용으로 남겨도 된다) |
| `POST /api/persona/revert` | 그대로 |
| `GET /api/persona/[version]` (신규, 디버그용) | 그 버전의 조립 결과 미리보기 (노트 선택 포함) |
| `POST /api/chat` | 응답 노드는 그대로. `ModelCall`에 `usedNoteIds` 기록 |

## 8. 안전 장치 요약
1. 안전 규칙은 ①고정층 맨 앞. 노트·수치는 항상 그 아래다.
2. 수치는 정해진 문장 표로만 프롬프트에 들어간다(자유 글 없음), 범위 0.2~0.8, 한 번에 ±0.1.
3. 노트는 한 줄·해요체·근거 2개 이상·개인정보 모양과 지시 낱말 금지.
4. 자동 적용 없음. 항목마다 사람이 승인.
5. 노트 10개 상한, 프롬프트에 들어가는 노트는 6개 상한 → 프롬프트가 부풀지 않는다.
6. 모든 변화에 근거 번호가 붙어, 어디서 왔는지 디버그 화면에서 추적된다.

## 9. 전후 비교 (3단계의 핵심 가설 검증)

전시의 핵심은 "REM을 하면 답이 정말 달라 보이는가"다. 이 구조는 달라진 이유를 **항목 하나로 가리킬 수 있어서** 설명이 쉽다.

1. REM 전: 확인 질문(`prompts.md` 7절)을 던져 답을 저장.
2. 제안 승인 후: 같은 질문을 다시 던져 답을 저장.
3. 화면: 전후 답을 나란히 + "이번에 켜진 노트 / 바뀐 수치"를 같이 표시.
4. 기준: 같은 질문 3개에서 달라진 예시를 기록한다. 달라지지 않으면 노트 선택 규칙과 수치 문장 표를 먼저 손본다 (프롬프트를 통째로 고치기 전에).

## 10. 모드 1·모드 2와의 관계

| 모드 | 역할 | 제안에 주로 기여하는 것 |
| --- | --- | --- |
| 1 정리 (깊은 잠) | 노드를 순서대로 읽으며 통찰을 쌓아 정리 | `addNote` / `editNote` (반복되는 패턴 → 지침) |
| 2 꿈 (REM) | 무작위 두 기억을 짝지어 연결 찾기 (온도 높임) | `moveStyle`과 드문 `addNote` (뜻밖의 연결 → 분위기) |

두 모드 모두 통찰까지만 만들고, 제안 생성(5절)은 **공통 마지막 단계** 하나다. 모드를 새로 추가해도 제안·검증·승인 코드는 그대로다.

## 11. 하지 않는 것 / 열린 질문

**하지 않는다**
- **관람객 간 기억 공유** ("오늘 전시장에 지친 분이 많았어요" 같은 앞 관람객 분위기를 은근히 녹이기): 기획서의 "관람객별 초기화"와 충돌하고 개인정보 위험이 있다. 나중에 하려면 개인을 못 알아보는 통계 수준(예: 하루 단위 분위기 수치 하나)으로만, 별도 설계로.
- **인격 본문 전체를 모델이 다시 쓰기**: 1절의 한계 때문에 하지 않는다.

**열린 질문**
- [ ] 말투 축 4개가 맞는가. (전시 컨셉에 더 보이는 축이 있으면 바꾼다. 축을 바꾸는 비용은 문장 표 3개씩이다)
- [ ] 노트 상한 10개, 프롬프트 6개가 적당한가. (전시 하루 동안의 학습량 대비)
- [ ] 노트 `cues`를 모델이 정하게 할지, 의미 파일의 `keywords`를 그대로 쓸지. (후자가 더 단순하다)
- [ ] 노트 선택에 임베딩을 쓸지. (6개 이하면 필요 없다. 노트가 많아진 뒤에 붙인다)
- [ ] 항목별 승인을 관람객이 직접 할지, 운영자만 할지.

## 12. 구현 순서 (backend-plan.md 7절 단계에 끼워 넣기)

1. **(바로 가능, 동작 변화 없음)** `src/lib/persona/assemble.ts`: ①+②+③ 조립 순수 함수. 노트 없음·수치 0.5면 지금 프롬프트와 같음을 단위 테스트로 증명. `/api/chat`이 이 함수를 쓰도록 바꾸고 `ModelCall`에 `usedNoteIds`.
2. `types.ts` 확장(3절)과 시드 이전. `data/store.json`의 인격에 `style`·`notes`.
3. **3단계(REM 모드 1)와 함께** `src/lib/persona/validate.ts` + 제안 생성(5절). `prompts.md` 6절을 구조화 출력(JSON 스키마)으로 교체.
4. **4단계** 항목별 승인·버전·되돌리기 API(6·7절). `tests/api-proposal.spec.ts`를 항목 단위로 고친다.
5. **5단계** 모드 2는 제안 생성 단계를 공유. 디버그 화면에 노트·수치·"이번 답에 켜진 노트" 표시.
6. 화면(B): 제안 카드를 항목 목록으로, 전후 비교 화면(9절).

각 단계 끝 기준: 단위 테스트(순수 함수) + API 테스트 + 같은 질문 전후 답 기록.
